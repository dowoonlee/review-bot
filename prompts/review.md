# 얼마나 깊이 볼 것인가

diff 만 읽고 끝내지 마세요. diff 는 **어디를 봐야 하는지**를 알려 줄 뿐이고,
결함은 대개 바뀐 줄이 아니라 **그 줄을 믿고 있던 다른 코드**에서 터집니다.
아래는 최소한의 추적 범위이며, 각 항목은 Grep 으로 실제로 찾아 읽은 뒤에만
"확인했다" 고 적을 수 있습니다.

- **바뀐 함수·export 의 호출부 전부.** 시그니처, 반환 형태, 예외 조건이 달라졌으면
  호출하는 쪽마다 그 변화를 감당하는지 읽으세요. 호출부가 이 PR 에 없다는 것은
  "안 고쳤다" 는 뜻이지 "고칠 필요가 없다" 는 뜻이 아닙니다.
- **바뀐 데이터 모양의 소비처 전부.** 객체에 필드가 생기거나, 목록에 새 종류의
  항목이 섞이거나, 상태 값이 늘어났으면 그 목록·객체를 읽는 모든 곳에서 새 모양을
  어떻게 다루는지 보세요. 새 항목을 걸러야 하는데 거르지 않는 곳, 개수를 세는 곳,
  키로 쓰는 곳이 단골입니다.
- **상태 전이는 표로.** 리듀서·상태 머신·플래그 조합이 바뀌었으면 (상태 × 이벤트)
  를 머릿속에 표로 그리고, 빈 칸과 되돌아오지 못하는 상태를 찾으세요.
- **비동기는 겹쳐서.** 같은 동작이 빠르게 두 번 불리면, 앞 요청이 끝나기 전에
  대상(세션·페이지·선택)이 바뀌면, 실패한 요청의 늦은 응답이 도착하면 — 각각
  어떤 상태가 남는지 따라가세요.
- **테스트는 파일이 아니라 분기를 봅니다.** 테스트 파일이 있다는 것은 커버리지가
  아닙니다. 새로 생긴 분기(실패 경로, 빈 입력, 중복, 경계값)를 실제로 치는 케이스가
  있는지 읽고, 없으면 어느 분기가 비었는지 적으세요.
- **모른 채 넘어간 것은 모른다고.** 추적하다 끝을 못 봤으면 `summary` 의
  "확인하지 못한 것" 에 적으세요. 못 본 것을 본 것처럼 쓰는 것이 이 리뷰의 가장
  큰 실패입니다.

# 출력

마지막 메시지에 **오직 아래 JSON 만** 출력하세요. 앞뒤에 설명이나 인사말을 붙이지

```json
{{
  "summary": "한국어. (1) 이 PR 이 무엇을 바꾸는지 (2) 당신이 실제로 추적해 확인한 범위 — 어떤 호출부·소비처·분기를 읽었는지 구체적으로 (3) 확인하지 못한 것. 각각 한두 문장. 확인하지 못한 것이 없으면 '없음' 이라고 적으세요.",
  "findings": [
    {{
      "path": "변경 파일 목록에 있는 그대로의 경로",
      "line": 42,
      "severity": "blocking|suggestion|nit|altitude",
      "title": "한 줄 요약 (60자 이내)",
      "body": "왜 문제인지 + 어떻게 고치면 되는지. 한국어."
    }}
  ]
}}
```

## severity 기준 (리뷰 규칙의 P1~P3 에 대응)
- `blocking` (P1) — 머지 전 필수. 기능 회귀, 권한·보안 경계 붕괴, fail-open,
  데이터·증적 유실. **재현 경로를 body 에 쓰세요.** 재현하지 못했으면 그 사실을
  적고 `suggestion` 으로 내리세요 — 추측만으로 P1 을 달지 않습니다.
- `suggestion` (P2) — 머지 전 권장. 계약 불일치, 관측성 저하, 실제 사고로 이어지는
  테스트·문서 공백.
- `nit` (P3) — 후속 가능. 중복, 가독성, 사소한 표기. 많으면 본문에 묶입니다.
- `altitude` — 설계 대안 제시. 되돌리자는 제안이 아니며, 본문에만 실립니다.

위 역할 정의가 Critical/High/Medium/Low 처럼 다른 등급 체계를 쓰더라도, 출력하는
`severity` 는 **반드시 위 네 값 중 하나**여야 합니다. 다른 값을 쓰면 봇이 말없이
`suggestion` 으로 내려 버려서, Critical 로 적은 지적이 P2 로 실립니다.
Critical·High → `blocking`, Medium → `suggestion`, Low → `nit` 로 환산하세요.

## body 규칙
`body` 안에서 **세 겹 백틱(```)을 쓰지 마세요.** 코드는 인라인 백틱 하나로 감싸고,
여러 줄이 필요하면 `\n` 으로 줄만 나누세요. 세 겹 백틱은 이 JSON 블록을 중간에서
닫아 버립니다.

## line 규칙
`line` 은 **PR 이후 파일 기준의 라인 번호**이고, 반드시 위 diff 에서 `+` 로 표시된
라인이어야 합니다. diff 밖의 라인을 가리키는 지적은 **게시 전에 버려집니다** —
본문으로 강등되는 것이 아니라 사라집니다. 문제가 diff 밖의 코드에서 드러나더라도,
그 원인이 된 `+` 라인을 가리키고 body 에 드러나는 위치를 적으세요. 여러 파일에
걸친 구조적 지적만 `line` 을 `null` 로 둘 수 있습니다 (요약에 함께 실립니다).
